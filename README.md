## ۱. مرور کلی

فلسفه ارزیابی این داشبورد در یک قاعده خلاصه می‌شود:

```text
مؤلفه                          = واحد شواهد      (id, name, observation)
رابطه مؤلفه ↔ رکن/هدف/اقدام   = ارزیابی         (target, weight, achievement)
رکن / هدف / اقدام              = تجمیع وزنی ارزیابی مؤلفه‌های متصل به آن
راهبرد                         = مشتق از اقدامات عضو (وارد امتیاز کل نمی‌شود)
امتیاز کل سند                  = تجمیع وزنی ۴ رکن چشم‌انداز
```

نتیجه این معماری:

1. **مؤلفه جای وزن و درصد نیست.** یک مؤلفه فقط «شواهد» است: شناسه، عنوان و وضعیت مشاهده‌شده. هیچ وزنی، درصد تحققی، امتیازی یا سابقه ادغامی داخل مؤلفه نگه داشته نمی‌شود.
2. **ارزیابی در «رابطه» انجام می‌شود.** برای هر جفت (مؤلفه، والد) یک رکورد مستقل با وزن، درصد تحقق و تارگت/معیار اختصاصی همان سطح وجود دارد. یک شواهد مشترک می‌تواند در رکن با یک معیار و در هدف دیگر با معیار و حتی درصد متفاوت ارزیابی شود.
3. **هر والد، تجمیع وزنی روابط خودش است.** هیچ امتیازی از سطحی به سطح دیگر «ارث» نمی‌رسد و راهبردها دوباره وارد امتیاز کل نمی‌شوند.
4. **عملکرد واقعی رسمی، روایت شواهد است، نه یک عدد موازی.** درصد تحقق، بازه عدم‌قطعیت و وضعیت همیشه از داده‌های ارزیابی و به‌صورت داینامیک ساخته می‌شوند، بنابراین امکان تناقض میان متن و درصد محاسبه‌شده از بین می‌رود.

**قابلیت‌های کلیدی:**

- 🧩 **تب مرکزی مؤلفه‌ها:** ۳۴ مؤلفه دقیقاً یک‌بار در یک فهرست؛ فقط شواهد و اتصال‌ها، بدون هیچ وزن یا امتیاز.
- ⚖️ **ویرایش ارزیابی در سطح رابطه:** وزن، درصد تحقق و «تارگت/معیار ارزیابی» هر مؤلفه در هر رکن/هدف/اقدام، مستقل و درجای همان تب.
- 🔒 **جداسازی سطوح:** عنوان و شواهد مؤلفه در تب‌های رکن/هدف/اقدام فقط‌خواندنی است؛ تنها از تب مرکزی تغییر می‌کند و فوراً در همه تب‌ها منتشر می‌شود.
- 🔗 **پرش دوجهته:** از قرص‌های اتصال هر مؤلفه به کارت رکن/هدف/اقدام مقصد.
- 💾 **ذخیره خودکار** نسخه کاری در مرورگر + پشتیبان JSON + خروجی HTML خودبسنده.
- 🏢 **شاخص مشارکت سازمانی:** سهم دستگاه‌های مسئول و همکار بر پایه نقش‌های درج‌شده در ۱۷ اقدام.
- 🎲 **مونت‌کارلو** (۲۰٬۰۰۰ تکرار) + مدیریت چالش‌های راهبردی موج دوم.

## ۲. اجرا و انتشار

**روش ۱ — باز کردن مستقیم:** فایل `index.html` را دابل‌کلیک کنید. داده جاسازی‌شده، استایل و منطق همه داخل همان فایل است و داشبورد کار می‌کند.

**روش ۲ — سرو محلی (توصیه‌شده):**

```bash
# در ریشه پروژه
python -m http.server 8000
# سپس در مرورگر: http://localhost:8000/index.html
```

سرو محلی توصیه می‌شود چون: فایل `data.json` بیرونی خوانده می‌شود (بدون محدودیت `file://`)، فونت/لوگو بدون خطای امنیتی بارگذاری می‌شوند و «بارگذاری فایل JSON از دیسک» بی‌دردسر است.

### ۲.۱ انتشار روی GitHub Pages

خروجی نهایی یک سایت ایستا است؛ کافی است فایل‌های لازم در شاخه انتشار (معمولاً `main`) و پوشه ریشه (`/`) قرار بگیرند:

1. فایل‌های حداقلی لازم برای اجرای داشبورد:

   ```text
   index.html
   data.json
   favicon.svg
   Sahel-VF.woff2
   Logo-shora.png
   ```

2. در مخزن GitHub: **Settings → Pages → Source: Deploy from a branch → Branch: `main` / `root`**.
3. آدرس نهایی: **<https://tavousi.github.io/Cognitive_sci_eval/>**

نکته‌های انتشار:

- **`data.json` باید همیشه با داده جاسازی‌شده در `index.html` یکسان باشد.** داشبورد ابتدا `./data.json` را می‌خواند و فقط در نبود یا نامعتبر بودن آن به داده جاسازی‌شده برمی‌گردد؛ بنابراین اگر فایل بیرونی قدیمی‌تر از فایل جاسازی‌شده باشد، سایت منتشرشده داده قدیمی را نشان می‌دهد. پیش از هر انتشار، پشتیبان JSON تازه را جای `data.json` بگذارید (یا آن را حذف کنید تا داده جاسازی‌شده مبنا شود). در مخزن فعلی این دو یکسان‌سازی شده‌اند.
- پوشه‌ها و فایل‌های منبع (`old/`, `hanan/`, `setade olome shenakhti/`, `پوراعتماد/`, `گزارس ستاد علم/`, `scripts/`, `.freebuff/`, فایل حجیم `thread-*.md`) برای اجرای داشبورد لازم نیستند؛ نگه‌داشتنشان برای آرشیو بی‌ضرر است، اما برای سبک‌تر شدن انتشار می‌توانید آن‌ها را خارج کنید.
- اگر لازم شد Jekyll فایل‌ها را دست‌کاری نکند، یک فایل خالی `.nojekyll` در ریشه اضافه کنید. (در حال حاضر هیچ فایل/پوشه‌ای با پیشوند `_` وجود ندارد و این مرحله اختیاری است.)

**پیش‌نیازها:**

- مرورگر مدرن (Chrome / Edge / Firefox). صفحه کاملاً RTL و فارسی است.
- برای **نمایش نمودارها** دسترسی به اینترنت لازم است (Chart.js از CDN). جداول، محاسبات و مدیریت داده بدون اینترنت هم کار می‌کنند.
- فایل‌های `Sahel-VF.woff2`، `Logo-shora.png` و `favicon.svg` باید کنار `index.html` باشند؛ در غیر این‌صورت فونت پیش‌فرض سیستم و آیکن جایگزین استفاده می‌شود.

## ۴. معماری ارزیابی

### ۴.۱ چهار سطح سند

| سطح | ماده سند | تعداد | واحد ارزیابی |
|---|---|---|---|
| چشم‌انداز (رکن) | ماده ۴ | ۴ رکن | روابط ارزیابی مؤلفه‌های متصل + تحلیل رکن |
| اهداف کلان | ماده ۵ | ۷ هدف | روابط ارزیابی مؤلفه‌های متصل + تارگت کلان |
| راهبردهای کلان | ماده ۶ | ۶ راهبرد | مشتق از اقدامات عضو (`linkedActionIds`) |
| اقدامات اجرایی | ماده ۷ | ۱۷ اقدام | روابط ارزیابی مؤلفه‌های متصل + دستگاه مسئول و همکار |

هر سطح، **درصد تحقق، وضعیت و بازه عدم‌قطعیت ۹۰٪** دارد. وزن هیچ‌کدام از این سطوح «داخل خودشان» نیست؛ وزن، خاصیت **رابطه** مؤلفه با آن سطح است.

### ۴.۲ مؤلفه = واحد شواهد

مؤلفه کوچک‌ترین و تنها واحد ثبت شواهد است و فقط این اطلاعات را نگه می‌دارد:

| فیلد | توضیح |
|---|---|
| `id` | شناسه پایدار مؤلفه، مانند `C01` … `C34` (موارد جدید `C35`, `C36`, …) |
| `name` | عنوان مؤلفه |
| `observation` | وضعیت مشاهده‌شده / شواهد عینی — **فیلد یکسان برای همه مؤلفه‌ها** |
| `visionIds[]` | اتصال‌های مؤلفه به ارکان چشم‌انداز (آینه‌ی مشتق‌شده از `relations[]`) |
| `goalIds[]` | اتصال‌های مؤلفه به اهداف کلان (آینه‌ی مشتق‌شده) |
| `actionIds[]` | اتصال‌های مؤلفه به اقدامات اجرایی (آینه‌ی مشتق‌شده) |

**آنچه به‌عمد در مؤلفه وجود ندارد:** `weight`، `achievement`، `weightedScore`، `parentWeights`، `mergedFrom`، `absorbed`، `mergedGroups`، `gid`، «مؤلفه اصلی/پیوندی» و هر یادآوری از فرایند ادغام. فیلدهای مشاهده نیز یکسان‌سازی شده‌اند: نام‌های قدیمی `actual` و `evidence` هنگام بارگذاری به `observation` نگاشت می‌شوند.

**۳۴ مؤلفه و ۷۱ رابطه جاری:** در سطح رکن ۱۲ رابطه، در سطح هدف ۱۹ رابطه و در سطح اقدام ۴۰ رابطه وجود دارد (۱۲ + ۱۹ + ۴۰ = ۷۱)، پراکنده روی ۲۸ والد (۴ رکن + ۷ هدف + ۱۷ اقدام). یک مؤلفه می‌تواند هم‌زمان در چند سطح و چند والد ارزیابی شود (مثال: `C01` در ۱ رکن، ۲ هدف و ۱ اقدام). جزئیات پشتوانه هر عدد در [EVIDENCE-REPORT.md](EVIDENCE-REPORT.md) آمده است.

### ۴.۳ رابطه ارزیابی — محل واقعی وزن و درصد

برای هر جفت (مؤلفه، والد) یک رکورد مستقل در `relations[]` نگه داشته می‌شود:

```text
Relation
    componentId   شناسه مؤلفه، مانند C01
    level         vision | goal | action
    parentId      شناسه والد (رکن، هدف یا اقدام)
    target        تارگت / معیار قابل سنجش همین مؤلفه در همین سطح
    weight        وزن مؤلفه در همین والد (۰ تا ۱۰۰)
    achievement   درصد تحقق مؤلفه در همین والد (۰ تا ۱۰۰)
```

نمونه واقعی از داده جاری — مؤلفه `C01` در چهار والد مختلف با چهار وزن مستقل:

```text
C01  «رتبه و حجم تولید علم: مقالات معتبر و استنادات بین‌المللی…»
 ├─ vision 1   weight 40   achievement 90
 ├─ goal   2   weight 30   achievement 90
 ├─ goal   7   weight 40   achievement 90
 └─ action 12  weight 40   achievement 90
```

شواهد یک‌بار در `C01.observation` ثبت شده است، اما ارزیابی آن در هر سطح مستقل است: تغییر درصد تحقق `C01` در رکن ۱ **هیچ تأثیری** بر درصد تحقق همان مؤلفه در هدف ۲، هدف ۷ یا اقدام ۱۲ ندارد. (این جداسازی سطوح به‌صورت خودکار در مرورگر آزموده شده است.)

`relations[]` **منبع حقیقت** است؛ آرایه‌های `visionIds/goalIds/actionIds` فقط آینه‌ی مشتق‌شده‌ی آن‌اند و در `normalizeDataset` هم‌گام می‌شوند.

### ۴.۴ قواعد اتصال

- اتصال‌ها **فقط از تب مرکزی «مدیریت یکپارچه مؤلفه‌ها و شواهد»** مدیریت می‌شوند.
- یک مؤلفه می‌تواند هم‌زمان به **چند رکن، چند هدف و چند اقدام** متصل شود. هیچ سقف تعداد و هیچ مفهوم «والد اصلی» یا «والد پیوندی» وجود ندارد.
- هیچ الزامی به داشتن اتصال در هر سه سطح نیست؛ ترکیب‌های معتبر شامل فقط-رکن، فقط-هدف، فقط-اقدام یا هر ترکیب دیگر است.
- **راهبرد مقصد اتصال مؤلفه نیست.** راهبردها به اقدامات متصل‌اند و امتیازشان از اقدامات مشتق می‌شود.
- مؤلفه بدون اتصال با نشان هشدار **«⚠️ بدون اتصال»** در فهرست مرکزی مشخص می‌شود و در گزارش اعتبارسنجی شمرده می‌شود. (در داده جاری: صفر مورد.)
- هیچ رابطه‌ای بی‌والد نمی‌ماند: در `normalizeDataset` روابط تکراری و روابط با مؤلفه/والد ناموجود حذف می‌شوند.

### ۴.۵ فرمول‌های محاسبه

همه محاسبات در تابع `recalcAll()` و پس از هر تغییر دوباره اجرا می‌شوند:

| سطح | فرمول |
|---|---|
| **هر والد (رکن/هدف/اقدام)** | `تحقق = Σ(وزن رابطه × تحقق رابطه) ÷ Σوزن روابط` روی روابط همان والد |
| **وزن کامل والد** | `weightSum = Σوزن روابط`؛ فقط اگر `|weightSum − 100| < 0.01` باشد والد «وزن‌کامل» است |
| **راهبرد** | `تحقق = Σ(وزن اقدام × تحقق اقدام) ÷ Σوزن اقدامات عضو` — وزن پیش‌فرض اقدام: ۱ |
| **امتیاز کل سند** | `تحقق = Σ(وزن سناریوی رکن × تحقق رکن) ÷ Σوزن ارکان` — و **فقط** اگر مجموع وزن‌های چهار رکن برابر ۱۰۰٪ باشد |
| **میانگین‌های توصیفی** | میانگین ساده (بدون وزن) روی تحقق همان سطح؛ در رابط کاربری صریحاً با برچسب «میانگین ساده» نمایش داده می‌شود |

نمونه محاسبه: اگر اقدامی سه رابطه با وزن‌های ۴۰/۳۰/۳۰ و تحقق‌های ۹۰/۸۵/۳۰ داشته باشد →
`(40×90 + 30×85 + 30×30) ÷ 100 = 64.5٪`

**قاعده وزن ناقص:** اگر مجموع وزن روابط یک **رکن چشم‌انداز** برابر ۱۰۰٪ نباشد، امتیاز کل سند محاسبه و نمایش داده **نمی‌شود** (به‌جای عدد، پیام «با وزن ناقص در ارکان، محاسبه کل انجام نمی‌شود» نشان داده می‌شود). برای والدهای غیررکنی، امتیاز با هشدار قرمز «(ناقص — باید ۱۰۰٪ باشد)» نمایش داده می‌شود و در گزارش اعتبارسنجی ثبت می‌گردد. **هیچ عددی برای تکمیل وزن‌ها حدس زده نمی‌شود.**

### ۴.۷ بازه عدم‌قطعیت ۹۰٪ (مدل‌محور)

- این بازه **فاصله اطمینان آماری کلاسیک نیست**؛ بازه‌ای مدل‌محور است که از **سیگمای کالیبره‌شده** ساخته می‌شود: `CI = امتیاز ± 1.645×σ` (Z بحرانی ۹۰٪).
- برای هر گره، σ از فیلد `uncertaintySigma` خوانده می‌شود؛ در نبود آن، از بازه قبلی یا از **پراکندگی وزنی** روابط همان والد مشتق می‌شود.
- **حداقل نیم‌پهنای بازه ۱.۵ درصد** است (`MIN_CI_HALF_WIDTH`)، بنابراین نقطه برآورد همیشه داخل بازه می‌ماند و بازه‌های بی‌معنا باریک نمی‌شوند.
- بازه **دینامیک** است: با هر تغییر وزن یا درصد تحقق، بلافاصله جابه‌جا می‌شود.
- بازه کل سند با **انتشار خطای جذر مجموع مربعات (RSS)** و فرض استقلال ارکان محاسبه می‌شود: `σ_کل = √Σ(سهم رکن × σ_رکن)²`.
- در خروجی (metadata) هم روش با نام `calibrated-sigma-model` و سطح اطمینان `۰.۹` ثبت می‌شود.

### ۴.۹ راهبردها: مشتق از اقدامات

- عضویت هر اقدام در راهبرد با `strategies[].linkedActionIds` تعیین می‌شود و `actions[].strategyId` از آن مشتق می‌گردد (تک‌منبع بودن رابطه).
- جابه‌جایی اقدام میان راهبردها از مودال «✏️ ویرایش اقدام» (تابع `setActionStrategy`) هر دو طرف را هم‌گام می‌کند.

سه سطح اول **میانگین ساده** هستند و تنها سطح چهارم، امتیاز وزنی کل سند است. این چهار عدد **چهار مرحله متوالی یک محاسبه علّی نیستند** و داشبورد هیچ ادعای «نشت کارایی» یا رابطه علت‌ومعلولی میان آن‌ها نمی‌کند؛ هدف، مقایسه‌ی چندسطحی برای دیدن فاصله‌هاست. متن همین هشدار داخل خود کارت نمودار هم نمایش داده می‌شود.

### ۴.۱۱ شاخص مشارکت سازمانی

برای تب «🏢 دستگاه‌های مسئول و همکار»:

- نام دستگاه‌ها از فیلدهای `owner` (مسئول) و `collaborators` (همکار) هر اقدام استخراج، یکسان‌سازی و یکتاسازی می‌شوند.
- هر **مسئول اصلی ۲ امتیاز** و هر **همکار ۱ امتیاز** برای هر ثبت نقش می‌گیرد.
- سهم هر دستگاه = امتیاز موزون آن ÷ مجموع امتیازهای همه نقش‌های ثبت‌شده (به‌صورت درصد). برای اینکه جمع سهم‌ها دقیقاً ۱۰۰٪ نمایش داده شود، خطای گِردکردن در آخرین ردیف جبران می‌شود.
- این شاخص **درصد تحقق، سهم بودجه یا سنجش عملکرد دستگاه نیست**؛ یک شاخص توصیفی از **مشارکت ساختاری بر پایه نقش درج‌شده** است. همین توضیح در metadata (`agencyParticipationMethod`) و در بنر خود تب هم ثبت شده است.
- اصلاح عنوان یا نقش دستگاه‌ها فقط از طریق «✏️ ویرایش اقدام» در تب اقدامات انجام می‌شود.

### ۴.۱۲ شبیه‌سازی مونت‌کارلو

- **۲۰٬۰۰۰ تکرار** در هر اجرا؛ برای هر رکن، تحقق از توزیع نرمال حول امتیاز جاری با σ همان رکن نمونه‌برداری و با وزن‌های سناریوی فعال به امتیاز کل تبدیل می‌شود.
- آماره‌های خروجی: **میانگین**، **میانه (P50)**، **صدک ۵٪ (P5)**، **صدک ۹۵٪ (P95)** و **احتمال تحقق بالای ۵۰٪**.
- نمودار: هیستوگرام ۳۰ سبدی از توزیع تجمیعی تحقق کل سند.
- اگر امتیاز کل سند به‌دلیل وزن ناقص ارکان قابل محاسبه نباشد، همه آماره‌ها `—` می‌مانند (هیچ عددی ساخته نمی‌شود).

## ۶. تب مدیریت یکپارچه مؤلفه‌ها و شواهد

این تب **مرکز واقعی داشبورد و تنها محل مدیریت مؤلفه‌ها و اتصال‌هاست**. گردش کار درست این است:

```text
۱) تب 🧩  →  ۳۴ مؤلفه را ببینید؛ عنوان و وضعیت مشاهده‌شده را تکمیل/اصلاح کنید و اتصال‌ها را تعیین کنید
۲) تب 👁️  →  برای هر مؤلفه وزن و درصد تحقق آن را در همان رکن تعیین کنید
۳) تب 🎯  →  همین کار را برای هر هدف کلان انجام دهید
۴) تب 📋  →  همین کار را برای هر اقدام انجام دهید
۵) داشبورد همه سطوح را از همین داده‌ها محاسبه می‌کند
```

### ۶.۱ فهرست مرکزی ۳۴ مؤلفه

- جدول دقیقاً **۵ ستون** دارد: `#`، `شناسه`، `عنوان مؤلفه`، `وضعیت مشاهده‌شده / شواهد عینی`، `اتصالات`.
- **هیچ وزنی، درصد تحققی، امتیازی، رنگی‌سازی بر پایه تحقق یا بازه عدم‌قطعیتی در این جدول نیست** — ارزیابی در تب‌های رکن/هدف/اقدام انجام می‌شود.
- هر مؤلفه **دقیقاً یک‌بار** نمایش داده می‌شود، حتی اگر به چند رکن/هدف/اقدام متصل باشد.
- کارت‌های آماری بالای جدول: کل مؤلفه‌ها، دارای وضعیت مشاهده‌شده، دارای اتصال (و تعداد بدون اتصال)، روابط ارزیابی.
- مؤلفه بدون اتصال با نشان **«⚠️ بدون اتصال»** مشخص می‌شود.
- جستجوی زنده در **شناسه، عنوان و متن شواهد**.

### ۶.۲ ویرایش

- **➕ افزودن مؤلفه جدید:** شناسه یکتا تولید می‌شود (`C35`, `C36`, …). شناسه‌های قبلی پس از حذف **دوباره شماره‌گذاری نمی‌شوند**.
- **✏️ ویرایش:** عنوان و وضعیت مشاهده‌شده در موجودیت مرکزی ذخیره می‌شود؛ با ذخیره، همه تب‌ها بلافاصله به‌روز می‌شوند.
- **🗑️ حذف:** حذف مؤلفه و همه روابط ارزیابی آن (با تأیید).
- **🔗 اتصال:** چیپ‌های 👁️ رکن (۴ مقصد) / 🎯 هدف (۷ مقصد) / 📋 اقدام (۱۷ مقصد)؛ کلیک = اتصال/قطع، بدون سقف تعداد. افزودن اتصال یک رابطه جدید می‌سازد و حذف اتصال، رابطه متناظرش را حذف می‌کند. **راهبرد در این مودال وجود ندارد.**
- **قرص‌های اتصال** روی هر ردیف: هر سطح یک قرص دارد و کلیک روی آن به **کارت همان مقصد** در تب مربوطه پرش می‌کند (با اسکرول نرم).

## ۹. داده، پشتیبان‌گیری و نسخه‌ها

### ۹.۱ اولویت بارگذاری داده (هنگام باز شدن صفحه)

```text
۱) فایل بیرونی ./data.json            → اگر موجود و ساختارش معتبر باشد
۲) داده جاسازی‌شده در <script id="embeddedDataset"> داخل index.html
۳) نسخه کاری ذخیره‌شده در مرورگر       → فقط اگر dirty=true باشد، روی مورد بالا سوار می‌شود
```

منبع فعال در متغیر `DATA_SOURCE` («فایل بیرونی data.json» / «داده جاسازی‌شده در index.html» / «نسخه محلی ذخیره‌شده» / «فایل واردشده: …») ثبت می‌شود و نشانگر بالای صفحه وضعیت ذخیره (`● تغییرات جاری` یا `✓ ذخیره‌شده`) را نشان می‌دهد. اگر هیچ منبعی در دسترس نباشد، پیام خطای واضح در صفحه نمایش داده می‌شود.

> **هشدار همگامی:** چون `data.json` اولویت دارد، نگه‌داشتن یک `data.json` قدیمی در ریشه مخزن باعث می‌شود سایت منتشرشده داده قدیمی نشان دهد. در مخزن فعلی، `data.json` با داده جاسازی‌شده یکسان است (۰ تفاوت در همه بخش‌ها). پس از هر ویرایش مهم، «دانلود پشتیبان JSON» بگیرید و آن را جای `data.json` بگذارید.

### ۹.۲ ذخیره خودکار و نسخه‌ها

- کلید ذخیره: `cognitive-dashboard-v3` در `localStorage` با محتوای `{ schemaVersion: 3, savedAt, dirty, source, data }`.
- کلید قدیمی `cognitive-dashboard-working-copy-v2` و هر payload با `schemaVersion` ناسازگار **پاک** می‌شوند تا داده قدیمی دوباره وارد داشبورد نشود.
- هر تغییر (ویرایش مؤلفه، اتصال، وزن، تحقق، تارگت، عملکرد، چالش) بلافاصله در نسخه کاری مرورگر ذخیره می‌شود.
- پس از **دانلود پشتیبان JSON یا نسخه HTML**، وضعیت به «ذخیره‌شده» تغییر می‌کند و نسخه کاری محلی پاک می‌شود (چون خروجی، سند مرجع جدید است).
- نشانگر بالای صفحه همیشه وضعیت را نشان می‌دهد: ● تغییرات جاری / ✓ ذخیره‌شده.
- بازگشت به نسخه مبنا، import، reset و export همه از **همان ساختار واحد v3** استفاده می‌کنند.

### ۱۰.۱ فیلدهای کلیدی

| فیلد | نوع | توضیح |

## ۱۳. محدودیت‌ها و هشدارها

1. **بازه عدم‌قطعیت، آماری نیست.** مدل‌محور و بر پایه سیگمای کالیبره‌شده است؛ آن را «فاصله اطمینان نمونه‌گیری کلاسیک» تفسیر نکنید. همین هشدار در metadata خروجی هم ثبت می‌شود.
2. **جمع وزن روابط هر والد باید ۱۰۰٪ باشد.** برای ارکان، نقض این قاعده امتیاز کل سند را غیرقابل‌محاسبه می‌کند؛ برای سایر والدها امتیاز با هشدار «وزن ناقص» نمایش داده می‌شود. هیچ عددی برای تکمیل وزن‌ها حدس زده نمی‌شود.
3. **همگامی `data.json` و داده جاسازی‌شده** بر عهده کاربر است؛ فایل بیرونی اولویت دارد (بخش ۲ و ۹.۱).
4. **عمومی‌بودن شواهد:** پیش از انتشار عمومی مخزن، بازبینی کنید که متن شواهد و نام دستگاه‌ها قابل انتشار باشند.
5. **اینترنت برای نمودارها** لازم است؛ در محیط بدون اینترنت، نمودارها خالی می‌مانند ولی جداول، محاسبات و مدیریت داده کامل کار می‌کنند.
6. **ذخیره‌سازی محلی وابسته به مرورگر است**؛ حالت ناشناس یا پاک‌سازی حافظه مرورگر، نسخه کاری را از بین می‌برد. برای کار جدی پشتیبان JSON بگیرید.
7. **بدون همکاری همزمان چند کاربر:** ذخیره‌سازی محلی است؛ برای کار تیمی، فایل JSON را ردوبدل کنید (یا داده را از طریق مخزن Git نسخه‌بندی کنید).
8. **آستانه‌ها، اوزان و درصدها تصمیم ارزیاب‌اند**؛ هر تغییر باید مستند و آگاهانه باشد و پیش از آن پشتیبان گرفته شود.
9. **مرجعیت متن‌ها:** عنوان مؤلفه‌ها و متن شواهد از دو گزارش رسمی استخراج شده‌اند؛ تأیید نهایی مرجعیت آن‌ها بر عهده متولیان سند است. تعارض‌های دو گزارش (مثلاً «۶۰ محصول» در برابر «۵۳ محصول») در متن شواهد با ذکر هر دو رقم افشا شده و هیچ عددی بدون پشتوانه وارد نشده است.
10. **`scripts/to_persian_digits.py`** ابزاری کمکی و دارای مسیر پیش‌فرض داخل کد است؛ پیش از استفاده، مسیر فایل ورودی را به‌عنوان آرگومان بدهید.

## ۱۴. گردش کار پیشنهادی

1. **اجرا:** داشبورد را با سرو محلی باز کنید (بخش ۲) تا `data.json` هم خوانده شود.
2. **مدیریت شواهد:** تب 🧩 — هر ۳۴ مؤلفه را بازبینی کنید: عنوان و وضعیت مشاهده‌شده را دقیق کنید و اتصال‌ها را به رکن/هدف/اقدام درست برقرار کنید. مؤلفه‌های «⚠️ بدون اتصال» را تعیین تکلیف کنید.
3. **ارزیابی ارکان:** تب 👁️ — برای هر مؤلفه، تارگت/معیار این سطح را بنویسید و وزن و درصد تحقق را تعیین کنید. مجموع وزن‌ها را روی ۱۰۰٪ نگه دارید.
4. **ارزیابی اهداف:** تب 🎯 — همان کار برای ۷ هدف؛ تفاوت معیار تحقق یک مؤلفه در هدف نسبت به رکن را همین‌جا اعمال کنید.
5. **ارزیابی اقدامات:** تب 📋 — همان کار برای ۱۷ اقدام؛ دستگاه مسئول و همکاران را در «✏️ ویرایش اقدام» به‌روز کنید.
6. **تصویر کلان:** تب 📊 — امتیاز کل سند، بازه ۹۰٪، نمودار مقایسه چندسطحی و جدول عملکرد ارکان را ببینید. سناریوی وزن‌دهی مناسب (متوازن/تخصصی/کاربر) را انتخاب کنید.
7. **مشارکت سازمانی:** تب 🏢 — سهم دستگاه‌های مسئول و همکار را برای گزارش‌دهی سازمانی مرور کنید.
8. **ریسک و آینده:** تب 🎲 — مونت‌کارلو را اجرا و چالش‌ها و راهکارهای موج دوم را تکمیل کنید.
9. **خروجی:** «دانلود پشتیبان JSON» برای نسخه‌بندی/ادامه کار و «دانلود نسخه کامل HTML» برای ارائه به‌عنوان فایل خودبسنده. برای انتشار سایت، پشتیبان JSON را جای `data.json` بگذارید و commit کنید.

## ۱۵. واژه‌نامه

| اصطلاح | تعریف |
|---|---|
| **مؤلفه** | واحد مرکزی شواهد: شناسه + عنوان + وضعیت مشاهده‌شده (بدون وزن و درصد) |
| **رابطه ارزیابی** | رکورد مستقل جفت (مؤلفه، والد) با `target`، `weight` و `achievement` |
| **تارگت / معیار رابطه** | شرط یا شاخص قابل سنجشی که تحقق همان مؤلفه در همان سطح با آن سنجیده می‌شود |
| **والد** | رکن چشم‌انداز، هدف کلان یا اقدام اجرایی |
| **شواهد عینی** | مستند، عدد، گزارش یا وضعیت مشهودی که تحقق مؤلفه را پشتیبانی می‌کند |
| **تحقق (Achievement)** | درصد پیشرفت ۰–۱۰۰ که از میانگین وزنی روابط همان والد به‌دست می‌آید |
| **وزن کامل والد** | مجموع وزن روابط والد دقیقاً ۱۰۰٪ باشد |
| **وضعیت (Status)** | یکی از پنج سطح: تکمیل‌شده، دستاورد عینی، خروجی اولیه، فعالیت اولیه، مغفول |
| **بازه عدم‌قطعیت ۹۰٪** | بازه مدل‌محور «امتیاز ± ۱٫۶۴۵σ» (نه اطمینان آماری کلاسیک) |
| **عملکرد واقعی رسمی** | روایت رسمی و قابل ویرایش شواهد یک هدف/اقدام؛ درصد تحقق در فیلد جداگانه محاسبه می‌شود، نه در این متن |
| **میانگین ساده** | میانگین بدون وزن تحقق اعضای یک سطح؛ فقط توصیفی و برچسب‌دار، و هرگز با امتیاز کل سند یکی گرفته نمی‌شود |
| **مشتق‌شدن راهبرد** | امتیاز راهبرد = میانگین وزنی اقدامات عضو (`linkedActionIds`)؛ راهبرد مقصد اتصال مؤلفه نیست |
| **شاخص مشارکت سازمانی** | سهم نسبی دستگاه‌ها از امتیازهای نقش (مسئول ۲ / همکار ۱) — نه درصد تحقق و نه بودجه |
| **نسخه مبنا (Baseline)** | داده مبنای بارگذاری‌شده که با «بازنشانی» برمی‌گردد |
| **نسخه کاری (Working Copy)** | تغییرات جاری ذخیره‌شده در `localStorage` مرورگر |
| **P5 / P50 / P95** | صدک‌های توزیع مونت‌کارلو (برآورد ریسک؛ P5 به‌عنوان VaR) |
| **AIE** | اقتصاد اطلاعات کاربردی — چارچوب اندازه‌گیری سند (داگلاس هابارد) |
| **schemaVersion 3** | نسخه معماری داده: «۳۴ مؤلفه مرکزی + روابط ارزیابی» |
